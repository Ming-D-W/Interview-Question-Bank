## 前端基础

### 浏览器相关

#### 输入 URL 会发生什么？

**核心思路**：围绕「请求构建 → 资源获取 → 页面渲染 → 缓存复用」四个阶段展开描述。

**完整流程**：

1. **URL 判定与规范化**：
   - 判断输入是搜索词还是 URL；主机名含非 ASCII 时进行 Punycode 编码；路径/查询按规范进行百分号编码与归一化。
   - 浏览器检查预加载 HSTS 列表，命中则直接使用 HTTPS 访问，避免首跳明文与降级攻击。
2. **地址解析（DNS Lookup）**：
   - 浏览器/OS/路由器/ISP 多层缓存未命中时，递归解析获取 IP；可能使用 DoH/DoT 进行加密解析。
   - CDN 场景中可能结合 ECS（EDNS Client Subnet）影响就近调度；IPv6/IPv4 并行采用 Happy Eyeballs 降低连接延迟。
3. **建立连接**：
   - **TCP 握手** 建立可靠连接；
   - **TLS 握手（HTTPS）** 完成证书链校验与密钥协商。TLS 1.3 将握手降至 1-RTT，并支持会话复用；也可能通过 Alt-Svc 升级到 **HTTP/3（QUIC）**，以缓解 TCP 队头阻塞（0-RTT 需注意重放风险）。
4. **发送请求**：
   - 构造 HTTP 报文（方法、路径、头、主体）。`Accept`、`Accept-Encoding`（br/gzip）、`Accept-Language` 等影响内容与压缩协商。
   - 跨域场景可能先发预检（OPTIONS），并通过 `Access-Control-Max-Age` 缓存预检结果；页面可借助 `dns-prefetch`/`preconnect` 提前解析与建连。
5. **服务器处理并响应**：
   - 负载均衡与 CDN 就近命中后回源；响应采用合适压缩与缓存指令（见下）。可用 `stale-while-revalidate`/`stale-if-error` 提升稳定性。
6. **浏览器渲染**：
   - 解析 HTML 得到 DOM，解析 CSS 生成 CSSOM，合并为渲染树；完成布局与绘制，合成线程/显卡参与渲染。
   - 预加载扫描器与 `async`/`defer`/`type="module"` 优化脚本阻塞；返回/前进可能命中 bfcache 即时恢复。
   - 若注册了 Service Worker，导航与资源请求可被拦截以实现离线与预取（Navigation Preload 可降低冷启动延迟）。

**缓存策略**：

- **强缓存**：通过 `Cache-Control: max-age/immutable`、`Expires` 等控制；命中直接本地返回。对 HTML 入口建议较短 `max-age` 或配合 `no-cache`，并使用带哈希的静态资源（JS/CSS/图片）。
- **协商缓存**：强缓存失效或标记 `no-cache` 时，携带 `If-None-Match`/`If-Modified-Since` 询问服务器；未变更返回 `304`。建议同时配置 `ETag` 与 `Last-Modified`。
- **可用性增强**：结合 `stale-while-revalidate`/`stale-if-error`，在回源或异常时优雅降级；与 CDN 缓存策略一致化可提升命中率。
- **与 SW 的配合**：HTTP 缓存与 Service Worker 的 Cache Storage 要避免冲突（慎用 `no-store`），静态资源可采用“网络优先 + 回退”或“缓存优先 + 回源刷新”。

> 面试作答时，可按照「URL 规范化/HSTS → DNS → TCP/TLS/HTTP3 → HTTP 协商/压缩 → CDN/服务端处理 → 渲染 → 缓存/SW」的顺序讲述，并结合资源提示与跨域预检等细节体现深度。

#### window.onload 和 DOMContentLoaded 的区别

- **window.onload**：需要等到当前页面所有的第三方资源加载完毕后才会触发
- **DOMContentLoaded**：等到DOM构建完毕后直接触发（jQuery的 `$.ready()` 或 `document.addEventListener('DOMContentLoaded')`）

### 事件机制

#### addEventListener 和 onclick 的区别

1. **addEventListener 可以叠加**：多次绑定会全部触发
2. **onclick 会覆盖**：多次绑定，后面的会把前面的覆盖掉，只会触发最后一次绑定的事件
3. **addEventListener 可以设置捕获阶段**：可以设置事件在捕获阶段执行
4. **addEventListener 可以解绑**：使用 `removeEventListener` 解绑（匿名函数无法取消）
5. **onclick 解绑**：直接设置为 `null`

## 网络请求

### 请求控制

#### 多个相同的请求，只想要最后一次请求结果

**核心策略**：为每次请求维护对应的 `AbortController` 实例，发起新请求前主动取消上一次，从而保证只保留最新响应。

**实现要点**：

1. **控制器复用**：在组件/服务作用域内持有 `AbortController` 引用，每次发起请求前先调用旧实例的 `abort()`，再创建新实例，避免“僵尸响应”写入状态。
2. **Axios 适配**：axios 1.4+ 原生支持 `signal`，旧版本需要借助 `AbortController` polyfill 或使用 `CancelToken`。请求拦截器中也可以统一注入 `signal`。
3. **异常处理**：调用 `abort()` 会触发 `DOMException`，在 `catch` 中需判断 `err.name === 'AbortError'` 并静默处理。
4. **兼容性**：`AbortController` 支持 Chrome 66+、Safari 12.1+ 等现代浏览器，低版本可降级为标记位 + 手动忽略回调。

::: details Axios 配合 AbortController 示例

```javascript
let controller;

export async function fetchLatest(query) {
  if (controller) controller.abort();
  controller = new AbortController();

  try {
    const { data } = await axios.get('/foo/bar', {
      params: { q: query },
      signal: controller.signal,
      timeout: 8000
    });
    return data;
  } catch (err) {
    if (err.name === 'AbortError') {
      // 主动取消时直接返回
      return;
    }
    throw err;
  }
}
```

:::

### Ajax原理

**核心技术对比**：

| 对比维度 | `XMLHttpRequest` | `Axios`（基于 XHR） | `Fetch` |
| --- | --- | --- | --- |
| API 风格 | 事件回调 + 状态机 | Promise 封装，拦截器 | Promise 原生 |
| 默认行为 | 需手动处理 JSON、超时、取消 | 内置 JSON 解析、超时、表单序列化 | 无超时/取消（需 `AbortController`） |
| 跨域支持 | 支持，需结合 CORS/JSONP | 同 XHR | 同 XHR，内置 `credentials` 控制 |
| 错误处理 | `onerror`/`onreadystatechange` | `try...catch` 捕获 | 仅网络错误 reject，4xx/5xx 仍需 `res.ok` 判断 |
| 上传/下载进度 | 支持 `progress` 事件 | 内置上传/下载钩子 | 通过 `ReadableStream` 手动处理 |

**Ajax 请求生命周期示例（XHR）**：

```javascript
const xhr = new XMLHttpRequest();
xhr.open('GET', '/api/list', true);
xhr.responseType = 'json';

xhr.onreadystatechange = () => {
  if (xhr.readyState === 4) {
    if (xhr.status >= 200 && xhr.status < 300) {
      console.log(xhr.response);
    } else {
      console.error(xhr.statusText);
    }
  }
};

xhr.onerror = () => console.error('network error');
xhr.send();
```

**Fetch + Abort 示例**：

```javascript
const controller = new AbortController();

fetch('/api/list', {
  signal: controller.signal,
  headers: { 'Accept': 'application/json' }
})
  .then(async (res) => {
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    return res.json();
  })
  .catch((err) => {
    if (err.name === 'AbortError') return;
    throw err;
  });

// 需要取消时
controller.abort();
```

> 面试场景中，可从“浏览器原生能力 → 第三方库封装 → 现代 API 特性”三个层面梳理，特别强调错误处理、取消、跨域与并发控制等实践要点。

### HTTP与HTTPS

#### 总结

1. **HTTP**：明文传输
2. **HTTPS**：加密传输
3. **HTTP默认端口**：80
4. **HTTPS默认端口**：443
5. **加密算法**：对称加密、非对称加密、Hash算法
6. **HTTPS传输过程**：使用对称加密，传输前先用密钥加密，加密传输，目标端使用相同的密钥解密

#### 详细说明

1. **从 HTTP 到 HTTPS**：HTTP 明文传输，易被窃听/篡改/伪造；HTTPS 在 HTTP 与 TCP 之间增加了 TLS 层，通过加密 + 校验提升安全。
2. **TLS 握手核心流程**：
   1. 客户端发起 `ClientHello`，携带协议版本、随机数、支持的加密套件。
   2. 服务端返回 `ServerHello`、数字证书、协商的加密套件，可选发送 `ServerKeyExchange`。
   3. 客户端验证证书链（根证书 → 中间证书 → 站点证书），确认域名匹配、签名有效、证书未过期/吊销。
   4. 客户端生成前主密钥（pre-master secret），使用证书中的公钥加密后发送给服务器。
   5. 双方基于随机数 + 前主密钥推导出会话密钥，并互发 `Finished` 消息校验握手完整性。
3. **加密组合**：
   - **非对称加密**：仅用于握手阶段的密钥交换/身份校验。
   - **对称加密**：握手结束后对实际应用数据进行高效加密（AES/GCM 等）。
   - **消息认证码 / AEAD**：确保数据完整性与防重放（如 HMAC、GCM 自带的认证）。
4. **证书体系**：
   - **CA 角色**：根 CA → 中间 CA → 终端证书，浏览器内置信任根证书列表。
   - **OCSP/CRL**：用于检查证书是否被吊销。
   - **证书透明度 (CT)**：保障证书签发过程透明，降低伪造风险。
5. **性能与优化**：TLS 1.3 简化握手为 1-RTT，可与 HTTP/2、HTTP/3 配合；启用会话复用（Session ID/Session Ticket）可减少重复握手开销。
6. **风险提示**：
   - 若证书被盗/私钥泄露，需及时吊销并更换。
   - 中间人攻击可通过伪造证书实施，浏览器的证书校验是关键防线。
   - 自签名证书适用于内部环境，对外提供服务需购买受信任 CA 的证书。

> 面试时可结合 TLS 1.3、HTTP/3、HSTS、HPKP（已废弃）等扩展知识点，展示对网络安全生态的理解。

## Vue框架

### Vue Router

#### vue-router的路由跳转和location.href的区别

**Vue Router（history模式）**：

- 通过HTML5的History API实现路由跳转
- 当页面路由发生变化时，Vue Router会对浏览器的History API进行操作，实现无刷新页面的路由跳转
- 通过 `pushState()` 或 `replaceState()` 方法向浏览器的历史记录栈添加或替换新状态
- 在浏览器前进或后退操作时，通过 `popstate` 事件监听历史记录变化，进行相应的路由跳转

**location.href**：

- 页面会刷新

**Vue Router（hash模式）**：

- 监听路径变化使用 `onhashchange` 事件

## 组件封装

### 1. 分页组件

**适用场景**：分页切换需要同步重置列表位置（移动端长列表、管理后台多筛选条件页）。

**关键实现**：

1. 除了继承 ElementUI 分页器的 `current-page`、`page-size` 等属性外，额外定义 `autoScroll` 控制是否启动滚动动画，避免强行耦合到所有列表。
2. 通过 `v-bind="$attrs"` 与 `v-on="$listeners"` 透传未显式声明的属性、事件，确保对 ElementUI 原生能力的兼容性。
3. 在组件内部封装滚动逻辑，可根据场景选择 `window.scrollTo`、`element.scrollIntoView` 或结合 `requestAnimationFrame` 实现平滑滚动，并允许外部配置滚动容器。

**常见问题**：

- 不同布局下滚动容器不一致时需暴露 `scrollTarget`/`beforeScroll` 钩子，防止硬编码导致的定位错误。
- 当分页切换伴随筛选条件变化时，应在 watch 中区分触发源，避免重复滚动或多次发请求。

### 2. 弹层组件

**封装场景**：中后台中反复出现“带页脚按钮的对话框”，需要统一交互细节（按钮顺序、loading 状态、关闭策略）。

**关键实现**：

1. 基于 `el-dialog` 二次封装，将页脚按钮抽象为具名 slot 或 props，支持 `confirmLoading`、`confirmText` 等可配置项。
2. 通过 `v-bind="$attrs"` 继承尺寸、遮罩、关闭行为等属性，`v-on="$listeners"` 透传事件，保证默认行为与原组件保持一致。
3. 内部暴露 `beforeClose` 钩子，允许外部进行表单校验或二次确认，避免强制关闭。

**注意事项**：

- 需要考虑可访问性（聚焦管理、`aria-label`），并确保按下 Esc 或点击遮罩时的预期行为可配置。
- 当项目存在弹层嵌套时，需配合全局 `DialogStack` 管理 z-index，避免遮罩穿透。

### 3. 省市区联动组件

**封装场景**：物流项目中有很多省市区联动的场景，如果不封装，每次都得复制相同的逻辑

**架构思路**：

1. **默认值处理**：通过 `addressData` / `addressFromProcess` 初始化组件内部 state，并在 `watch` 中保持与外部 props 同步，避免首次渲染出现闪烁。
2. **级联加载**：
   - 监听省、市、区的变化后动态请求下一级列表，并在列表更新后提供合理默认值。
   - 若任一级被清空，需主动重置下游选择，保持数据一致性。
3. **数据透传**：将最终选中值组合为数组并通过 `this.$emit('input')` 实现双向绑定；对于大型表单，可额外暴露 `change` 事件提供完整地址对象。

**扩展建议**：

- 接入缓存层或预拉取热门城市，降低重复请求带来的延迟。
- 将行政区层级、过滤规则抽象为配置，便于切换不同国家/地区或自定义黑白名单。
- 若需支持“只选到市级”，可通过 props 控制展示层级，减少无意义的空选择器。

### 6. 远程搜索组件

**核心要素**：

**增强建议**：

- 可根据用户角色调整搜索池，避免展示无权限页面；必要时结合服务端接口实现真实远程搜索。

import path from 'path'

export default {
  name: 'HeaderSearch',
  data() {

      search: '',
      options: [],
      searchPool: [],
      show: false,
      fuse: undefined
    }
  },

      return this.$store.getters.permission_routes
    }
  },

    routes() {
      this.searchPool = this.generateRoutes(this.routes)
    },
    searchPool(list) {
      this.initFuse(list)
    },
    show(value) {
      if (value) {

      } else {
        document.body.removeEventListener('click', this.close)
      }
    }
  },

    this.searchPool = this.generateRoutes(this.routes)
  },
  methods: {
    click() {
      this.show = !this.show
      if (this.show) {
        this.$refs.headerSearchSelect && this.$refs.headerSearchSelect.focus()
      }
    },
    close() {
      this.$refs.headerSearchSelect && this.$refs.headerSearchSelect.blur()
      this.options = []
      this.show = false
    },
    change(val) {
      this.$router.push(val.path)
      this.search = ''
      this.options = []
      this.$nextTick(() => {
        this.show = false
      })
    },
    initFuse(list) {
      this.fuse = new Fuse(list, {
        shouldSort: true,
        threshold: 0.4,
        location: 0,
        distance: 100,
        maxPatternLength: 32,
        minMatchCharLength: 1,
        keys: [{
          name: 'title',
          weight: 0.7
        }, {
          name: 'path',
          weight: 0.3
        }]
      })
    },
    generateRoutes(routes, basePath = '/', prefixTitle = []) {
      let res = []
      for (const router of routes) {
        if (router.hidden) { continue }
        const data = {
          path: path.resolve(basePath, router.path),
          title: [...prefixTitle]
        }
        if (router.meta && router.meta.title) {
          data.title = [...data.title, router.meta.title]
          if (router.redirect !== 'noRedirect') {
            res.push(data)
          }
        }
        if (router.children) {
          const tempRoutes = this.generateRoutes(router.children, data.path, data.title)
          if (tempRoutes.length >= 1) {
            res = [...res, ...tempRoutes]
          }
        }
      }
      return res
    },
    querySearch(query) {
      if (query !== '') {
        this.options = this.fuse.search(query)
      } else {
        this.options = []
      }
    }
  }
}
</script>

## 工程化

### Git操作

#### Git Stash（代码暂存）

**使用场景**：

在功能分支开发过程中遇到紧急线上缺陷，需要暂存本地工作切换到 master/hotfix 分支。

**操作要点**：

1. **暂存代码**：使用 `git stash push -m "feature-wip"` 存储当前修改；若需连同未跟踪文件一起暂存，使用 `git stash push -u`。
2. **查看记录**：`git stash list` 快速确认当前栈内容，避免误删。
3. **恢复代码**：`git stash pop` 会自动应用并删除记录；若担心冲突可先 `git stash apply` 验证，再配合 `git stash drop` 清理。

**冲突处理**：

- 恢复时若出现冲突，按照普通合并冲突方式解决后继续 `git add` + `git stash drop`。
- 若 stash 中包含构建产物，建议在恢复前手动清理 `dist` 等目录，减少冲突。

### 项目流程

#### 从需求到上线的完整流程

**角色说明**：

- **产品经理**：负责出原型稿
- **项目经理**：把控整个项目进度

**完整流程**：

1. **需求来源**：
   - 产品经理产出需求
   - 组长通过禅道/TB分配需求

2. **Bug管理**：
   - 测试人员在TB上提缺陷任务
   - 通过钉钉通知开发人员

3. **Bug状态流转**：
   - **待解决**：测试刚测出bug，开发还未解决
   - **已解决**：开发改完bug，测试还未复测（如果未改完，测试会reopen，影响绩效）
   - **已完成**：开发改完bug，测试复测通过

4. **前后端联调**：
   - 前端接入后端真实接口进行自测
   - 确保整体流程可以跑通
   - **接口文档管理**：ApiFox（通过后端代码生成）/YApi/Word/Markdown
   - **接口Mock**：前端使用MockJS或后端提供的Mock接口（通过ApiFox生成）

5. **需求评审**：
   - **参与人员**：产品经理 + 后端 + UI + 项目经理 + 测试人员 + 组长（可选）
   - **确定时间**：前端开发时间 + UI设计时间 + 后端开发时间 + 联调时间 + 测试时间 + 上线时间

6. **时间评估**：
   - 项目经理定时间，开发人员评估是否可完成
   - 如果完成不了，需告知项目经理或组长评估其他解决方案
   - **时间过长**：提前完成后，组长会安排其他小bug处理
   - **时间过短**：提前告知风险，重新排期或安排其他人员协助

7. **开发阶段**：
   - 完成功能开发
   - 前后端联调确保流程跑通

8. **测试环境部署**：
   - 把代码提交到Git的dev分支
   - Push到远程仓库
   - Jenkins完成自动部署

9. **测试阶段**：
   - 测试人员进行测试
   - 发现bug提交到禅道并告知开发处理

10. **预发环境测试**：
    - 把代码提交到release（预发分支）
    - 测试人员在Jenkins平台点击预发布环境构建

11. **发布上线**：
    - 预发环境测试完毕后部署到线上
    - 测试人员到线上环境复测
    - 复测通过后把release合并到master，完成发布

**分支管理规范（Git Flow）**：

- **主干分支**：`master/main`（线上版本）、`develop`（日常集成）。
- **辅助分支**：
  - `feature/*`：新功能开发，基于 `develop` 分支创建；完成后合并回 `develop`。
  - `release/*`：发布前稳定期，基于 `develop` 创建；修复完成后合并回 `master` 与 `develop`。
  - `hotfix/*`：线上紧急修复，基于 `master` 创建；修复后合并回 `master` 和 `develop`。

**代码评审与自动化**：

1. **Code Review**：提交 PR 前保证本地 lint/test 通过，评审关注点包括业务正确性、异常处理、可读性与安全性。建议在 PR 描述中附上需求背景、测试截图、风险点。
2. **CI/CD 流水线**：
   - **持续集成**：自动执行 lint、单元测试、构建，阻止有问题的代码进入主干。
   - **持续交付/部署**：通过 Jenkins/GitHub Actions 等完成部署，需设置环境变量、密钥管理与回滚策略。
3. **常见风险**：
   - 环境差异导致的构建失败，需保持依赖版本锁定（如使用 `package-lock.json`）。
   - 数据迁移脚本上线失败，建议在预发环境演练并准备 rollback 脚本。
   - 缺乏监控与报警，导致问题难以及时发现，上线前应验证日志、APM、可观测性配置。

#### 3. 问题描述技巧

**描述框架**：问题 → 解决思路 → 方案思考（GitHub） → 最终落地方案（代码实现）

**示例1：大文件上传**

- **场景**：物流管理系统有上传视频功能，之前没有做切片上传
- **问题**：上传视频太大时，网络波动会导致上传终止，需要重新上传
- **解决方案**：大文件切片上传、断点续传

**示例2：多页签通信**

- **场景**：后台管理系统中，运营人员会通过多个浏览器Tab页面打开系统
- **问题**：A页签退出登录后登录其他用户，其他页签依旧处于第一个用户的登录状态（只有刷新后才会变成最新用户）
- **预期**：A页签退出登录后，其他页签也随之退出登录
- **解决方案**：
  - 在GitHub找相似实现案例
  - 使用 `BroadcastChannel`（浏览器提供的API）解决
  - 虽然 `onstorage` 也可以解决，但需要向本地存储写内容才会触发其他页签的事件
  - 我们只需要多页签通信，不需要往本地存储写内容
  - 所以最优方案是 `BroadcastChannel`

### 面试沟通技巧

#### 上家公司信息准备

- 上家公司规模（多少人）
- 团队规模（多少人）
- 项目开发时长、参与人数、负责模块
- 不能被面试官带节奏，按照自己的想法讲
- **保持自信**
